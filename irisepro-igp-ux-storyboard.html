Questions only you can answer

These are product calls, not code calls. Each one changes what gets built, so none of them should be guessed.

  1. What is www.igpnetwork.in? The marketing screen's QR code points there and the modal names it in copy. It resolves — 200, Hostinger CDN, on IPs unrelated to our infrastructure. Is it ours, a partner-agency microsite, or something abandoned? If it is not ours, the QR should not be shipping.
  2. Does the partner enter their own payout details, or does an admin? Today neither works: the signup UPI field is commented out, the dashboard card is @if(false), and the profile screen has no field. If partners self-serve, the dashboard block needs unhiding and update-payment needs authentication. If admin captures it, the wizard's "you can withdraw" promise must be rewritten.
  3. Is withdrawal partner-initiated or admin-initiated? The wallet screen tells the partner they will be able to withdraw after verification. The only payout code is storePayout, an admin form. There is no request-payout control anywhere. One of the two has to change.
  4. Two approval gates or one? status gates login; referral_status gates the referral link. Self-signup sets status active + referral locked; admin-create sets status inactive. Is the intended model "log in immediately, earn after approval", or "approved before anything"?
  5. Which Platinum number is real — ₹7,000 or ₹7,500? The writer pays 7,000; four screens promise 7,500 and the reward journey advertises "up to ₹20,000", which only adds up at 7,500. Whichever is correct, the other three copies have to be deleted rather than corrected — one table, one place.
  6. Is the "90-Day Clock" a real mechanic? The rewards screen describes a 90-day window to reach 100 enrolments. Nothing in the code ever compares now() to cycle_started_at; the cycle only advances when Platinum is hit, which resets the badge to none and enrolments to zero. Either the clock needs building or the copy needs removing.
  7. Should partners see each other? The leaderboard shows other partners' names, photos and enrolment counts. That is a deliberate motivational choice in most affiliate programmes and a privacy question in some — but it should be a decision, and right now it is a default.
  8. What happens to a partner's ledger when they are deleted? destroy() is a hard delete with no soft-deletes and no foreign keys, so rewards, transactions, badge history and the KYC row survive as orphans and the private S3 Aadhaar objects are never purged. Retention and erasure both need a stated rule.
  9. Do the six orphaned screens ship or get deleted? Reward journey, Terms of Service, programme overview, live Q&A, NDA status and certificate have zero inbound links. Each is either a nav item we forgot to add or dead weight to remove — but leaving them URL-only is the one option that helps nobody.
  10. Where does the referral link point once attribution is rebuilt? The partner surface is Laravel at app.irisepro.in/partners; the buyer surface is Next.js at yashho.com. The link has to land on the storefront and the code has to survive into the Razorpay order notes. That is a storefront change, and it should ship together with the double-credit fix.

Track H

Is the signed NDA tamper-evident?

No — and we already own the pattern that would make it so. The parent-consent ledger is a hash-chained, signed, WORM-backed record. The NDA is a file upload. Below: the delta, then a common rail so no future agreement has to reinvent it.

Four ways the signed NDA can be disputed today

H-1 — re-uploading destroys the previous signed agreement MobileIgpNdaController::uploadWalletDocs calls PrivateMedia::purgeAllDisks() on the NDA PDF and both Aadhaar images, then $igp->nda()->delete(), before writing the replacement. There is no supersession — only replacement. An authenticated partner can overwrite their own signed agreement at any time, including after approval, and the original is gone from the row and purged from both disks.
H-2 — nothing binds the stored PDF to the text that was displayed The agreement is rendered inline from activate-wallet.blade.php, while the file the partner downloads and signs is a separate static asset (images/pdf/IGP NDA.pdf). Nothing checks the two agree, and no hash of either is recorded. If a partner disputes a clause, we cannot establish which version of which text they signed.
H-3 — no approver identity, no approval time igp_ndas records status, remarks and updated_at. There is no approved_by and no approved_at. “Who approved this KYC, and when?” has no answer in the data — and per the access finding, the approve/reject routes are reachable without authentication at all, so there may not have been a person.
H-4 — storage is tamper-recoverable, not tamper-proof The media bucket has versioning enabled, so an accidental delete is recoverable by an operator. That is not the same as immutable: without Object Lock, a sufficiently privileged actor (or the application’s own purgeAllDisks) can remove the object and its versions. Aadhaar images and a signed contract belong on the WORM lane, alongside the consent ledger.

The proposal — one agreement rail

Generalise what the consent ledger already does so that signing anything with anyone is a plug-in, not a rebuild. The chain-hashing, signing and WORM machinery exists and is proven in production; what is student-shaped about it is only the two foreign keys.

The KMS signature is the load-bearing control The chain proves internal consistency — alter a row and its hash stops matching. But someone holding the DB credential could recompute the whole chain. They cannot forge the signature: the key lives in KMS, outside the database. That is the difference between “tamper-detectable by an honest process” and “tamper-evident against a privileged actor” — which is what audit grade means. Given G-01, the payout endpoint currently answers unauthenticated, this is not theoretical.

Applying accounting standards surfaced two things

The ledger is single-entry igp_transactions records credit/debit against one account. That is a running tally, not a book — no contra-entry, so no trial balance, and an unbalanced write is undetectable. Proper form posts two legs summing to zero (Commission Expense ↔ Partner Payable), which makes A7: every entry_group sums to zero a single arithmetic assertion.
pending_balance is the accrual account nobody implemented It exists, renders on the dashboard, and has zero write sites. Under accrual accounting money has three states — accrued (earned, unapproved), approved (payable), settled (paid). Today a commission jumps straight to approved_balance at webhook time, before KYC clears and before any refund window. That is why the missing clawback bites: we approve money we may have to recover from a balance a partner may already have withdrawn.
⭐ The payee is POLYMORPHIC — decided 4 Sep The ledger keys on payee_type + payee_id, never igp_id. Yashomargis and Yashodarshis are both payees — and Yashodarshis have no payment path at all today, measured 4 Sep.

This does not assert that evaluators are paid. It makes the ledger able to pay them without a migration — and retrofitting a polymorphic key through a live, hash-chained, trigger-guarded money table is the most expensive change this design can absorb.

Consequence: igps.approved_balance and pending_balance are retired, not migrated. A Yashodarshi has no row in igps, and RT-8 already says the balance must be a projection. One cached projection, payee_balances, keyed (payee_type, payee_id), written only by PayeeLedger as SUM(ledger).
The daily books check — ten assertions A1 chain + signature verify · A2 balance == ledger sum · A3 every credit traces to a captured payment · A4 one credit per reward row · A5 no credit against a refunded enrolment · A6 withdrawals reconcile to payouts · A7 every entry_group sums to zero · A8 no entry predates the last checkpoint · A9 control account agrees with the subsidiary ledger.

A1 answers “has anyone tampered?” A2–A9 answer “do the books balance?” — and A2 must be seeded to fail in tests. A reconciler that has never gone red is one nobody has proven can.

Keyed tokens, not masks — settled 4 Sep [Goutam] "even if we store we must store a token that cannot be identified to the person and cannot be misused by anyone." Masks were the earlier answer and they leak: XXXXX234F gives three digits and the check character of a PAN.

⛔ And a plain SHA-256 is not the fix — Aadhaar is 1012 values and PAN about 3×1011, so a GPU enumerates either in minutes. Only a keyed HMAC with the key outside the database works: irreversible without the key, still deterministic so a UNIQUE index catches one-person-many-accounts, and revocable — rotate the key and every token is inert. Reuses ConsentSigner's KMS GenerateMac, already in production.

The honest limit: tokens make the identifiers unusable; they do not anonymise the record, because we still hold name and address by design. The defensible sentence is "a leak exposes a partner's name and address, and their Aadhaar and PAN to nobody, ever."

Superseded note — "so there is no way anyone can misuse these ever." A database dump then contains nothing usable. Verification runs through an online partner service; we keep the mask and the reference, and the vendor is the custodian of record.

⛔ One consequence to decide, not discover: a TDS return needs the deductee's full PAN — Form 26Q cannot be filed against a mask. So someone holds it at filing time. Best answer: the KYC vendor, exchanged via the reference and never persisted. Alternatives: a tokenisation vault, or the CA directly. Deciding in January is too late.

And the rule is a ratchet, not a promise: a test scans every column of the partner tables — plus the ledger's JSON trace, the likeliest leak — for a PAN-shaped or 12-digit value, and is seeded to prove it can go red.
⛔ We cannot do this ourselves — and DigiLocker is the route Online Aadhaar eKYC returning demographic data requires KUA or sub-KUA status, restricted to regulated entities or their authorised technology partners. We are an edtech company, so a partner is not a convenience choice — it is how this feature exists at all.

DigiLocker is the cleaner shape and it is what Cashfree implements. The person authenticates on DigiLocker's own page and approves what is shared; the Aadhaar number never enters our form, our servers or our logs. We call create-url, they go and come back, we call get-document.

Corrected 4 Sep — an earlier version of this track drew the raw Aadhaar-number + OTP flow. That is a real mechanism, but it puts the number through our form for no benefit. DigiLocker does not.
