The irony worth fixing first

The onboarding welcome banner that names the programme renders only when funding_source ∈ {waiver, external, part_payment}. A Razorpay buyer carries funding_source = 'razorpay'.

The fee-waived demo student is told what programme they're in. The person who just paid ₹4,999 is not. Their screen says only "Tell us about you."

The rule that removes four disagreeing lists

Stream sets the SHAPE. DOB sets the LAW. Which fields appear, whether Board is asked, the copy register and the card's tag label are all per-family data. Minor status — consent basis, guardian OTP, "prepared for the family of" — is always server-recomputed age from DOB.

That deletes SCHOOL_STREAMS (declared twice), ADULT_STREAMS and the storefront's GUARDIAN_STREAMS as independent authorities.

One regression to guard before shipping

Student::isMinor() is fail-closed: a blank or unparseable DOB returns minor. Today ADULT_STREAMS masks that for adult streams by forcing false. Removing the list means an adult learner with a missing DOB would render as "prepared for the family of".

DOB is required at Step 1 for every family, so an onboarded learner should always have one — but that is an assumption, not a guarantee. It needs a test before the list is deleted.

  • Delete the funding_source gate on the welcome note
  • Part-payment: plan + ScorecardDelivery lock state, no paid figure
The money line is real — and already reconciled

The figure is not a plan price. payments carries one row per capture: the gross in payload['amount'] (paise) plus a per-transaction GST ledger — taxable_value, gst_amount, gst_rate — written at capture by Gst::splitFromGross() for GSTR filing and the GSTIN invoice.

₹5,898.82 is the codebase's own worked example: "captures 589882p, not 499900p" (PaymentController.php:1112). With GST off, Gst::breakup() collapses cleanly to ₹4,999 — so one component renders both states.

The learner sees the tax breakup once, then never again

Gst::breakup() — the declared single source for "the checkout summary / receipt display" — is called from CheckoutController, EnrolPaymentController and LandingController. It is called from zero frontendapp/* views.

So a buyer sees base + GST + total at checkout and, once inside the app, has no receipt at all. The banner should carry a Tax invoice affordance reading the same ledger row — the compliance surface and the "what did I buy" surface are the same screen.

Part-payment is the one exception. An instalment plan is admin-recorded offline with no Razorpay capture, so there is no payments row to total. That banner must show plan + settlement state, never a paid figure.

Confirmed — Sutirtha, 10 Aug

NEET/JEE take a Class dropdown, from Class 5. Not a generic stage list. Preparation starts around Class 8, and coaching institutes run NEET/JEE tracks from Class 5 — so the class is real, useful data for this stream. Only the repeat-year case needs a non-class option.

Option lists stay English-only. No kn translation needed — the lists are short, structured dropdowns, and a standard English set across streams is sufficient. This removes a blocker, not a corner: it means the option lists can be built as soon as the families land.

Career Readiness follows DOB. The stream explicitly includes Class 11 and 12, so it can have minors. DOB also gives us the age profile of who is actually joining the stream — useful beyond getting the consent and minor/adult experience right.

Still open

KMM's ratification on the Career Readiness split. Sutirtha has agreed; the minor-framing change touches the DPDPA consent surface, so it wants the second confirm before the guard tests go green and land.

Existing rows. IAS/KAS learners already onboarded carry whatever they typed. A backfill has to map those to a stage, or leave them blank and let the tag hide. Blank is safer — it loses nothing the engine uses. NEET/JEE rows are less affected: a value like "9" is already a valid Class option.
